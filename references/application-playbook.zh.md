# 投递操作手册

在基于浏览器的岗位投递、LinkedIn Easy Apply、Simplify、Greenhouse、Lever、Ashby、Workday 以及其他 ATS 页面上使用本参考。

## 全局规则

- 只计入已确认的提交。
- 优先选择简短、可靠的路径，而不是冗长的自定义表单。
- 在继续下一个之前，关闭每个已完成或已跳过岗位的标签页。
- 只保留需要转交用户的标签页。
- 在看板中记录每一个结果。
- 停下来，而不是绕过验证或猜测高影响答案。
- 不要分别建立「测试」和「正常」两套行为。使用同一种默认行为：自动填写明确的低风险字段，对缺失的高影响事实提出聚焦的问题，并始终在最终提交前停下。

## 表单答案默认值

- 具有明确档案值的基本字段可以自动填写：姓名、邮箱、电话、LinkedIn、地点、简历上传和入职日期。
- 仅当措辞与档案或答案库密切匹配时，才可以填写工作许可、雇主担保和薪酬。
- 除非用户配置了确切答案，自愿身份信息在可用时默认为留空、"Prefer not to say" 或拒绝申报/跳过。
- 自定义问题在已有答案库模式时使用这些模式。如果不存在模式，起草该具体答案并请用户确认。
- 最终提交始终需要用户批准。在最后一次点击之前展示简明摘要。

## 低摩擦投递

海投 Volume 和首次真实投递测试应优先选择低摩擦投递：

- 不创建新账号。
- 默认不使用 Workday、Oracle 或其他冗长的企业级 ATS。
- 没有视频、长篇写作样本或强制提交作品集。
- 最多一个自定义问题。
- 简历上传和最终确认的路径清晰。
- 没有 CAPTCHA、Cloudflare、登录或 2FA 中断。

这是优先级规则，不是永久禁止。在精投 Precision 下，高价值岗位在用户确认值得额外时间之后，可以为此使用 Workday、Oracle、长表单或更深入的自定义工作。

## 自动化阶梯

先使用最快的可靠方法，仅在需要时再升级：

1. 浏览器自动化 / Playwright 式控制：最适合批量工作、普通按钮、表单字段、清理标签页，以及可重复的 ATS 流程。
2. DOM 加键盘修复：当下拉菜单或浮层行为异常时，使用 Escape、Tab、Enter、方向键，并选择真实选项。
3. 视觉或 computer-use 控制：当页面状态在视觉上重要、按钮被遮住、下拉是自定义组件、上传没有可见反馈，或者 DOM 状态与可见状态不一致时使用。
4. 用户转交：用于 CAPTCHA、Cloudflare、登录、2FA、敏感的法律问题、缺失的材料或权限提示。

Playwright 是实现细节，不是面向用户的概念。除非用户询问技术细节，否则向用户把它描述为快速浏览器自动化。

## 10 个常见卡点

### 1. 权限

在长时间运行之前，验证 Agent 能够点击、阅读页面、切换标签页和上传文件。同时验证目标网站的浏览器扩展权限。

如果权限在运行中途失败，记录所需的确切权限，并停止该次投递。

### 2. 看起来已选中、实际并未选中的下拉

ATS 下拉可能在视觉上显示了某个值，但内部校验仍然失败。

尝试：

- 按 Escape 关闭自动填充浮层。
- 点击真实下拉选项的文本。
- 使用键盘导航。
- 如果普通 DOM 交互失败，使用视觉/计算机控制。
- 修复之后，验证网站不再报告该字段无效。

如果同一字段反复失败，记录一条卡点，而不是继续耗时间。

### 3. 地址与选项匹配

地址字段可能要求全称、缩写、城市、州、国家或本地化文本。

按以下顺序尝试，并根据用户档案调整：

1. 完整的城市、州、国家。
2. 仅城市。
3. 仅州。
4. 国家全称。
5. 国家缩写。
6. 在相关时使用当地语言变体。

对于自动完成字段，先输入，等待候选项出现，再选择一个候选项。除非网站接受自由文本，否则不要提交原始键入的文本。

### 4. Simplify 或扩展浮层挡住按钮

如果 Next、Review 或 Submit 没有响应：

- 关闭 Simplify 侧栏或其他浮层。
- 聚焦该按钮并按 Enter。
- 重试一次。
- 如果仍然被挡住，记录一条卡点。

除非确认规则通过，否则不要把该申请计入已提交。

### 5. 关闭已完成的窗口或标签页

每个岗位在提交、跳过或受阻之后，关闭不再需要的标签页。这使内存、页面脚本和 Agent 上下文保持可控。

只有在用户必须行动时才保持标签页打开，例如 CAPTCHA、登录、上传或最终人工审阅。

### 6. 严格定义提交成功

提交证据可以包括：

- 可见文本，例如 `Application submitted`、`Application sent` 或 `Thank you for applying`。
- 感谢页。
- 诸如 `thanks`、`thank-you`、`submitted` 或 `confirmation` 的 URL 模式。
- 平台状态明确写明申请已发送。

不要计入：

- 已保存的岗位。
- 岗位跟踪器。
- Simplify 的快速申请标签。
- 自动填充完成。
- 点击了提交按钮但没有确认。

### 7. 邮箱验证与 CAPTCHA / Cloudflare

如果用户已连接邮箱工具并授权读取验证码，可以处理邮箱安全码。

CAPTCHA、hCaptcha、reCAPTCHA、Cloudflare 和反爬检查必须视为转交用户。不要绕过它们。

### 8. 登录会话与账号选择

如果出现登录页，停下来并记录 `Login required` 或 `Session expired`。

除非用户明确指示且该流程是安全的，否则不要尝试自动登录。如果存在多个 LinkedIn 或邮箱账号，使用候选人档案或规则中指定的账号。

### 9. 简历上传验证

上传简历后，在提交之前验证文件已经附上。

注意：

- 只接受 PDF 的网站。
- 自定义上传组件。
- 静默的上传失败。
- 附上了错误的简历变体。
- 浏览器权限失败。

如果无法验证上传，标为 `Needs user` 或 `Blocked`；除非用户明确允许，否则不要在没有简历的情况下提交。

### 10. Goal 模式的预期

Goal 式运行最适合海投 Volume 和简短投递流程。

预期 Agent 会跳过或推迟：

- Workday 或 Oracle 这类账号步骤很多的流程。
- 冗长的自定义申请。
- 需要缺失材料的表单。
- 登录、2FA、CAPTCHA 或 Cloudflare。

对于高价值目标岗位，使用一次聚焦运行，而不是海投式 Goal。

## 常见 ATS 备注

### LinkedIn Easy Apply

- 优先使用较新的筛选条件，以及直接投递流程。
- 在点击 Next、Review 或 Submit 之前关闭浮层。
- 仅在看到已提交/已发送的确认之后才计入。

### Greenhouse

- 即使页面看起来正确，下拉校验也可能已经过期。
- 在重试提交之前，目视确认必填字段。
- 如果无效状态持续存在，记录确切字段和卡点。

Greenhouse 邮箱安全码标准作业程序：

- 仅在用户已授权邮箱访问时使用。
- 从邮件中读取最新的 Greenhouse 安全码。
- 尽可能定位每一个单字符安全码输入框。
- 输入前清空每个框。
- 使用聚焦按键，每个框输入一个字符，而不是整段粘贴。
- 读回这些值，并验证拼接后的验证码与邮件中的验证码完全一致。
- 仅在验证之后提交。
- 如果字符重复、显示为 `undefined`、无法清空或无法验证，停下来并转交用户。

### Lever

- 注意 hCaptcha 或最终确认页。
- 只计入明确的确认或感谢页。

### Ashby

- 通常需要上传简历。
- 继续之前验证上传。
- 如实记录文件权限卡点。

### Workday / Oracle / 企业级 ATS

- 除非匹配度很强，否则跳过或推迟冗长且以登录为主的流程。
- 记录维护、账号创建或登录卡点。
