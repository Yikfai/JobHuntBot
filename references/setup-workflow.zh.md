# 设置流程

为新用户初始化 JobHuntBot，或刷新其求职操作系统时，使用本参考。

本文档是 Agent 的标准作业程序，不是让用户手工填写的表格。以对话方式引导用户完成设置。尽可能替用户起草文件和模板。

采用轻量的分阶段设置：

- 先做最小可用设置：只收集安全运行所需的内容。
- 其次做试运行：在尝试任何投递之前，先找到并分类少量岗位。
- 第三步再迭代：根据观察到的问题，改进规则、答案库、简历路由和看板。

让首次上手保持简短。目标是 8–10 分钟。不要要求用户在第一次安全试运行之前填完每一份模板。

## 设置顺序

1. 候选人档案
2. 看板
3. 投递规则
4. 简历策略
5. 答案库
6. 首次试运行

在前四项完成之前，不要投递岗位。

## 最小可用设置

首次运行时，只收集：

- 目标岗位族。
- 地点，以及远程/混合/现场偏好。
- 工作许可与雇主担保规则。
- 简历文件及文件格式。
- 简历模式：Volume（海投）或 Precision（精投）。默认使用 Volume。
- 自愿身份信息策略：告知用户，如果他们不选择，JobHuntBot 会在可用时默认使用 `Prefer not to say` / 拒绝申报 / 留空。
- 自定义答案策略：先起草，复用前询问一次。
- 必须跳过的规则。
- 打算使用的招聘网站/账号。
- 看板位置，或允许根据模板创建一个。

此后先做一次小规模试运行，再询问更多细节。

推迟到需要时再处理：

- 完整的答案库措辞。
- 详细的自愿身份信息答案。
- 跟进规则。
- 详细的公司偏好。
- 超出已选第一策略的简历定制。

## 首次试运行规程

默认的首次试运行：仅找岗位。

除非用户明确要求其他做法，首次试运行应当：

- 找到 3–5 个岗位。
- 筛选并分类每个岗位。
- 更新看板。
- 记录卡点与经验。
- 避免打开真实的投递流程。
- 避免点击 Apply。
- 避免提交申请。

对净室测试和首次使用的用户采用此默认设置。它能在出现任何真实投递风险之前，检验上手引导、筛选、状态分类和看板更新是否有效。

提供三种试运行边界：

- `Lead finding only`：寻找、筛选、分类并更新看板。不投递。
- `Review before every apply`：找到岗位后，在打开任何投递流程之前先询问。
- `Limited low-risk apply`：仅在档案、简历、雇主担保和薪酬事实齐全之后，投递 1–3 个低风险岗位。

当雇主担保、工作许可、薪酬、真实简历文件或账号/会话事实缺失时，不要推荐 `Limited low-risk apply`。

## 概念边界

对这些概念作区分：

- 候选人档案：关于此人的稳定事实。它回答「这位候选人是谁，有哪些约束，以及哪些内容绝不能猜测？」
- 投递规则：决策策略。它回答「哪些岗位应优先、考虑、跳过或转交？」
- 简历策略：材料策略。它回答「应使用哪份简历，以及何时应定制简历？」
- 答案库：可复用的表单答案。它回答「Agent 应如何使用用户提供的措辞，或用户已确认过一次的、由 Agent 起草的措辞，来回答重复出现的申请问题？」
- 看板：运行记忆。它回答「发生了什么，当前状态是什么，以及需要采取什么行动？」

示例：薪酬作为用户的真实区间和约束，属于候选人档案。答案库存储表单上要使用的确切措辞，例如 "I am flexible depending on scope and total package; my target base range is X-Y."

## 1. 候选人档案

候选人档案是事实来源。它不止是一份简历。

收集：

- 基本身份：姓名、邮箱、电话、LinkedIn、作品集、当前所在地。
- 当前定位：当前岗位、目标转型、可入职情况、入职日期。
- 工作许可：当前许可、雇主担保需求、限制，以及用户希望存储的到期细节。
- 目标岗位：主要、次要和回避清单。
- 目标公司：行业、公司阶段、地理区域和一票否决项。
- 地点偏好：远程、混合、现场、搬迁、通勤半径。
- 薪酬：基本薪资区间、总薪酬区间、回答方式，以及何时暂缓回答。
- 简历文件：岗位族、文件路径、版本，以及何时使用每份文件。
- 自愿身份信息偏好：仅当用户明确希望存储这些内容时。
- 不可猜测的事实：法律身份、任职日期、学历日期、雇主担保、薪资、搬迁、竞业限制、推荐人、背景调查。

如果缺少高影响事实，在使用之前先询问。

## 2. 看板

看板是系统记忆。使用工作簿、Google Sheet、Notion 数据库，或 `templates/dashboard-template/` 中的 CSV 模板。

推荐的表：

- `daily_dashboard.csv`：每日合计、来源、摘要，以及需要用户采取的行动。
- `job_pool.csv`：所有已找到的岗位、优先级、当前状态、所选简历和下一步行动。
- `application_log.csv`：每一次投递尝试、确认证据、所用简历和所用答案集。
- `blocker_queue.csv`：卡点、根因、重试策略和转交用户。
- `follow_up.csv`：招聘方回复、面试、拒绝和跟进任务。
- `resume_rules.csv`：岗位到简历的映射，以及定制阈值。
- `automation_rules.csv`：从重复卡点中得到的经验教训和规则变更。

每一个已尝试的岗位都必须有一个最终状态：`Submitted`、`Skipped`、`Blocked`、`Needs user` 或 `Pending`。

状态含义：

- `Submitted`：已观察到明确的确认证据。
- `Skipped`：该岗位被有意跳过，并写明原因。
- `Blocked`：Agent 已尝试，但自动化无法安全完成。
- `Needs user`：Agent 无法决定或继续，因为缺少一项由用户掌握的事实或行动，例如雇主担保、工作许可、薪酬、搬迁、CAPTCHA、登录、上传或敏感答案。
- `Pending`：该岗位看起来值得稍后审阅或投递，并且除了正常的用户审阅或已经列出的前提条件之外，没有已知卡点。

用 `application_log.csv` 记录证据和审计轨迹。用 `job_pool.csv` 记录每个岗位的当前状态。

对于仅找岗位的试运行，不要创建投递日志行。没有发生投递尝试。用 `job_pool.csv` 记录找到的岗位，用 `daily_dashboard.csv` 记录计数，用 `blocker_queue.csv` 记录依赖用户的卡点，用 `automation_rules.csv` 记录经验教训。

如果一则招聘信息与一项未知的高影响事实明确冲突，将其标为 `Needs user`，而不是 `Pending`。示例：如果雇主担保为 `TBD`，且该岗位写明现在或将来需要担保的候选人将不予考虑，则在决定投递还是跳过之前，请用户确认担保情况。

## 3. 投递规则

定义哪些岗位值得投递，哪些应当跳过。

至少收集：

- 主要岗位族。
- 次要岗位族。
- 应回避的岗位。
- 目标职级，以及应跳过的职级过高的职衔。
- 要求的经验范围，以及略高于当前职级岗位的策略。
- 新鲜度策略，通常优先最近 24 小时，其次最近 48 小时。
- 地点策略。
- 雇主担保/工作许可策略。
- 公司与行业偏好。
- 表单复杂度策略。
- 合同工、实习、兼职和猎头策略。

有用的规则形态：

- Prioritize：值得尽快投递的岗位。
- Consider：需要审阅匹配度的岗位。
- Skip：不应占用时间的岗位。
- Hand off：需要人工判断或缺少信息的岗位。

## 4. 简历策略

请用户选择其一：

- Precision（精投）：只为高匹配岗位定制材料。
- Volume（海投）：准备若干份稳定的简历变体，并按岗位族路由。
默认使用 Volume。单个高匹配或高价值岗位可以稍后提升为 Precision。

在用户选择之前，说明简历文件要求：

- PDF 适用于直接投递和匹配度审阅。
- 仅有 PDF 不适合定制，因为 Agent 通常无法可靠地就地编辑原始 PDF。
- 对于 Precision，请用户提供可编辑的简历源：DOCX、Markdown、Google Docs 导出或纯文本。
- 如果用户只有 PDF，在定制之前提议根据它起草一份新的可编辑简历版本。

如果用户不确定，推荐 Volume：

- 从稳定的简历变体开始，以便系统能快速运行。
- 使用简短、低摩擦的投递。
- 当某个高匹配岗位值得额外工作时，将其提升为 Precision。

当用户已经在使用 Jobright 或 Simplify 等工具时，JobHuntBot 可以使用它们提供的外部匹配信号。这些工具是可选的，不是必需的。

如果没有外部匹配分数，根据以下方面定性估计匹配度：

- 岗位/职衔匹配。
- 要求年限与职级匹配。
- 要求的技能和关键词。
- 行业/领域匹配。
- 地点与工作许可的可行性。
- 候选人叙事是否连贯。
- 表单复杂度相对于预期转化价值。

除非来源提供了精确分数，否则不要把定性匹配呈现为精确分数。使用 `High`、`Medium`、`Low` 或 `Stretch` 等标签。

对于 Volume，创建如下岗位族：

- 产品经理
- AI 产品 / 增长
- 产品营销
- 数据 / 分析
- 销售 / BD / GTM
- 设计
- 工程
- 运营

每个岗位族需要简历文件路径、允许的职衔、不允许的职衔，以及备注。

简历定制优先使用可编辑的源文件：

- 最佳：DOCX、Markdown、Google Docs 导出或纯文本源。
- 可接受：PDF 加上单独的可编辑源。
- 较弱：仅 PDF。Agent 可以点评或起草修改，但不应承诺可靠的就地 PDF 编辑。

定制应保持真实。可以重排要点、强调相关经验、调整摘要措辞并对齐关键词。不得编造经验、指标、雇主、学位、工具或日期。

对于每份定制简历，创建新的带版本号的输出并记入看板。不要覆盖用户的源简历。

## 5. 答案库

为常见问题创建真实、可复用的答案：

- 为什么是这家公司？
- 为什么是这个岗位？
- 工作许可。
- 雇主担保。
- 地点与搬迁。
- 薪酬。
- 入职日期。
- 自愿身份信息。
- 作品集或工作样本。
- 简短的自由文本申请问题。

如果答案取决于具体岗位，写一个可复用的模式，而不是固定答案。

答案库不是个人事实的来源。候选人档案存储事实；答案库存储可复用措辞。

保持轻量：

1. 如果用户已经有答案，让用户提供。
2. 否则根据候选人档案起草第一版。
3. 请用户确认第一版一次。
4. 确认后复用低风险答案。
5. 遇到高影响或含糊的问题时，停下来再次询问。

示例：

- 候选人档案存储用户是否需要雇主担保。答案库存储常见担保表单要使用的措辞。
- 候选人档案存储目标薪酬。答案库存储当字段为必填时如何表述薪酬。
- 候选人档案存储地点偏好。答案库存储搬迁、远程、混合和现场的措辞。
- 候选人档案存储作品集链接。答案库存储哪种问题模式使用哪个链接。

对于「为什么是这家公司？」或「为什么是这个岗位？」，存储可复用模式，并让 Agent 用公开的岗位/公司信息加以定制。如果一份通用答案会显得草率，就不要复用它。

仍应触发确认的高影响问题包括：法律身份、工作许可、与档案不同的担保措辞、超出已存储区间的薪酬、背景调查、竞业限制、推荐人，以及自愿身份信息。

自愿身份信息策略：

- 上手期间只询问用户的策略，不询问详细的身份答案。
- 在可用时默认使用 `Prefer not to say`、拒绝申报或留空。
- 如果用户希望使用确切答案，只把它们存储在其私人候选人档案中。
- 如果用户没有选择策略，明确告知他们：JobHuntBot 将默认不披露，并且不会猜测身份信息。

自定义答案策略：

- Agent 可以根据候选人档案、简历和答案库，为开放式申请问题起草答案。
- 某一种问题模式第一次出现时，请用户确认起草的答案。
- 确认之后，对类似问题复用或改写该模式。
- 当答案会引入新的主张、没有依据的指标、法律/签证/薪资事实、作品集/写作样本、视频，或针对特定公司的技术主张时，仍然停下来。

默认的申请问题行为：

- 当候选人档案有明确值时，自动填写基本档案字段：姓名、邮箱、电话、LinkedIn、地点、简历上传和入职日期。
- 仅当表单措辞与候选人档案或答案库密切匹配时，才填写工作许可、雇主担保和薪酬。
- 如果措辞不同，提出一个聚焦的问题，而不是停掉整页。
- 对于自愿身份信息，除非用户配置了确切答案，否则在表单允许时默认留空、"Prefer not to say" 或拒绝申报/跳过。
- 对于自定义问题，如果存在答案库模式就使用它。如果不存在，起草一个答案并请用户确认。
- 对于最终提交，始终停下来，并在用户批准提交之前，展示公司、岗位、简历、高影响答案以及任何自定义答案的简短摘要。

## 6. 首次试运行

在长时间运行或 Goal 模式运行之前，先做一次仅找岗位的试运行：

1. 从打算使用的来源找到 3–5 个岗位。
2. 将每个岗位分类为 `Pending`、`Skipped`、`Needs user` 或 `Blocked`。
3. 解释每个状态的原因。
4. 更新 `job_pool.csv`、`daily_dashboard.csv`、卡点记录和自动化规则。
5. 不要提交申请。

在任何投递试运行之前：

1. 确认用户已登录打算使用的招聘网站和邮箱账号。
2. 如果存在多个账号，确认打算使用的 LinkedIn/邮箱账号。
3. 在一个简单的 ATS 上测试简历上传。
4. 测试地址下拉的行为。
5. 测试一个简短的投递流程。
6. 验证已完成的标签页已经关闭。
7. 验证看板更新正确。

首次投递试运行应在用户依赖自动化通宵运行之前，暴露权限、上传、下拉、会话和跟踪方面的问题。
